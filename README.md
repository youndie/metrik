# metrik

Лёгкий мониторинг Ktor-сервисов: один плагин в сервисе, один бинарь на сервере, один файл SQLite.

Ниша — между «логов пока хватает» и «поднимаем Prometheus + Grafana + Alertmanager». metrik
отвечает на четыре вопроса: сколько запросов, сколько ошибок, насколько медленно, не кончается ли
память — и пишет в Telegram, когда с ответами что-то не так.

## Подключение сервиса

```kotlin
install(Metrik) {
    service = "orders-api"
    apiKey = System.getenv("METRIK_KEY")   // один ключ на всю инсталляцию metrik
    endpoint = "metrik-ingest:9999"
    release = System.getenv("APP_VERSION") // необязательно; рисует отметки деплоя на графиках
}
```

Всё. Регистрировать сервис не нужно — он заводится сам при первом пакете. Через минуту в дашборде
появятся RPS, доля ошибок и p95.

Цена для сервиса: **106 нс на запрос** (замер, объект, неблокирующая отправка в канал) и один
UDP-пакет в минуту. Отказ metrik на целевой сервис не влияет никак: нет сервера, не резолвится
DNS, переполнена очередь — агент считает потерю и работает дальше.

## Запуск сервера

```bash
docker run -p 8080:8080 -p 9999:9999/udp \
  -v ./data:/data \
  -e METRIK_INGEST_KEY=<секрет> \
  ghcr.io/youndie/metrik:latest
```

В Kubernetes — Helm-чарт в [charts/metrik](charts/metrik). Дашборд едет отдельным
контейнером с nginx: отдавать wasm-бандл из нативного бинаря нечем.

**Два требования, которые нельзя игнорировать:**

* **Перед UI обязан стоять reverse proxy с аутентификацией** (oauth2-proxy, Traefik ForwardAuth,
  nginx `auth_request`). Своего логина у metrik нет — он доверяет заголовкам
  `X-Auth-Request-User` / `X-Auth-Request-Email`, и без прокси дашборд открыт всем, кто дотянулся
  до порта.
* **Ingest-порт (UDP) не выставлять наружу.** UDP не аутентифицируется и подделывается тривиально;
  ключ в пакете отсекает случайное, а не злонамеренное. Порт живёт внутри кластера.

## Из чего состоит

| Компонент | Что это | Стек |
|---|---|---|
| `:agent` | Ktor-плагин: меряет, агрегирует в минутное окно, шлёт по UDP | Kotlin Multiplatform (JVM + Native) |
| `:server` | принимает, хранит, считает алерты, отдаёт JSON | Kotlin/Native, Ktor CIO, SQLite (sqlx4k) |
| `:composeApp` | дашборд | Compose Multiplatform: wasm в проде, desktop для отладки |
| `:shared` | провод и контракт API | KMP, kotlinx.serialization |

Ключевое решение: **агрегирует агент, а не сервер.** Сервис на 1000 rps шлёт один-два пакета в
минуту вместо 60 000 датаграмм. Цена — приблизительные перцентили (±20 %), чего достаточно для
трендов и алертов и недостаточно для формального SLA-репортинга. Обоснование и остальные решения —
[docs/research/research-architecture.md](docs/research/research-architecture.md).

## Модель установки

Одна инсталляция принадлежит одной команде и мониторит сколько угодно сервисов, у каждого — сколько
угодно инстансов. Мультитенантности внутри нет: нужна изоляция от другой команды или другого
контура (test/prod) — поднимается вторая инсталляция, это один бинарь и один файл.

metrik мониторит и сам себя: `METRIK_SELF_SERVICE=metrik-server`. Сервер мониторинга, которого не
видно, — плохой сервер мониторинга.
