# research — архитектура metrik

Лёгкий мониторинг Ktor-сервисов: плагин-агент в целевом сервисе, самодостаточный нативный
сервер-приёмник с SQLite, дашборд на Compose Wasm. Ниша — между «логов достаточно» и «поднимаем
Prometheus + Grafana + Alertmanager»: один бинарь, один файл БД, ноль JVM в проде,
пять минут на подключение сервиса.

Документ фиксирует **проверенные факты** (что я реально прочитал в коде/артефактах), **принятые
решения** и **риски**. Всё, что не проверено, помечено как гипотеза.

---

## 1. Проверенные факты

### 1.1 Ktor plugin API — всё нужное есть в `commonMain`

Проверено по `ktor-server-core-jvm-3.5.1.jar` (в `~/.gradle/caches`) и по индексу Maven Central.

| Факт | Где проверено |
|---|---|
| Хуки `CallSetup`, `Metrics`, `ResponseSent`, `CallFailed`, `MonitoringEvent` | `io/ktor/server/application/hooks/*.class` |
| `Metrics` — отдельная ранняя фаза, предназначенная именно для замеров | там же |
| Шаблон маршрута достаётся из события `RoutingRoot.RoutingCallStarted` (публичный `EventDefinition<RoutingCall>`), оттуда `.route` | `io/ktor/server/routing/RoutingRoot$Plugin.class` |
| Штатный `MicrometerMetrics` **лениво проверяет** доступность JMX (`isManagementFactoryAvailable$delegate`) | `io/ktor/server/metrics/micrometer/MicrometerMetricsKt.class` |
| `ktor-server-core`, `ktor-server-sse`, `ktor-server-websockets` опубликованы под `linuxx64`/`linuxarm64` | листинг `repo1.maven.org/maven2/io/ktor/` |
| Актуальные версии: Ktor **3.5.2**, sqlx4k **1.13.0** | `maven-metadata.xml` обоих |

**Следствие 1.** Метка серии — это `RoutingCall.route` (`/users/{id}`), а не `call.request.path()`
(`/users/42`). В драфте был «путь запроса»; сырой путь взорвал бы кардинальность и сделал бы БД
бесполезной. Если событие роутинга не пришло (запрос не сматчился ни на один маршрут → 404, или
ответ выдан плагином до роутинга) — серия помечается `<unmatched>`.

**Поправка, найденная при реализации M2** (изначально здесь стояло «взять `routingCallKey`, как
делает `MicrometerMetrics`» — так нельзя):

* `routingCallKey` и хук `Metrics` **закрыты**: первый `internal`, второй `@InternalAPI`. Штатным
  плагинам Ktor это доступно, стороннему модулю — нет. Рабочая замена: событие
  `RoutingRoot.RoutingCallStarted` для маршрута и хук `CallSetup` для отметки времени. Атрибуты
  `RoutingCall` общие с исходным вызовом, поэтому метка доезжает до `ResponseSent`.
* `RoutingNode.toString()` печатает **все** селекторы ветки, а не путь: у `get("/users/{id}")`
  выходит `/users/{id}/(method:GET)`. Всё, что в скобках, приходится отбрасывать.
* `Dispatchers.IO` на Kotlin/Native `internal` — в `commonMain` его нет. `SelectorManager()` без
  аргументов сам выбирает диспетчер под платформу.

**Следствие 2.** Ktor сам не считает JMX гарантированно доступным. Значит и мы не считаем: базовый
набор системных метрик обязан работать без `java.management`.

### 1.2 UDP на Kotlin/Native — работает

Проверено по `ktor-network-macosArm64Main-3.4.2.klib`:

- `posix/src/io/ktor/network/sockets/UDPSocketBuilderNative.kt` — реализация `udpBind`/`udpConnect`;
- `DatagramSocketNative`, `BoundDatagramSocket`, `ConnectedDatagramSocket` присутствуют в нативном klib;
- приём датаграмм реализован через `produce` на `Dispatchers.IO`;
- в `Datagram.kt` есть проверка `require(remaining <= MAX_DATAGRAM_SIZE)` с сообщением
  «Datagram size limit exceeded»;
- артефакты `ktor-network-linuxx64` / `ktor-network-linuxarm64` опубликованы.

То есть «UDP-приёмник внутри нативного бинаря» — не спайк, а обычный код. Ограничение практическое,
не API-шное: **безопасный размер пакета ≈ 1200 байт** (типичный MTU 1500 минус IP/UDP-заголовки и
запас на оверлейную сеть k8s). Больше — фрагментация, а фрагментированная датаграмма теряется целиком.

Но **работает оно только с числовым адресом**: см. §1.6 — доменное имя на Kotlin/Native не
разрешается вообще, и это стоило нам полного молчания агента у всех нативных сервисов.

### 1.3 Отдача статики из нативного Ktor — больное место

Проверено по [katcher](https://github.com/youndie/katcher):

- весь Tailwind лежит **строковой константой** `const val CSS` в
  `server/src/commonMain/kotlin/ru/workinprogress/katcher/static/CSS.kt` (31 КБ исходника) и отдаётся
  из `ConfigureRouting.kt` через `respondText(CSS, ContentType.Text.CSS)`;
- UI рендерится сервером (kotlinx.html + HTMX), бандлера в проде нет вовсе.

Причина: `staticFiles`/`staticResources` в Ktor завязаны на `java.io.File`/classloader и в
`nativeMain` недоступны. Для Compose Wasm (мегабайты `.wasm` + `.js` + ассеты) трюк с константой не
масштабируется.

### 1.4 Системные метрики без JMX на JVM

Из `java.base`, без модуля `java.management`:

- `Runtime.getRuntime().totalMemory()/freeMemory()/maxMemory()` — heap;
- `Runtime.getRuntime().availableProcessors()` — знаменатель для CPU%;
- `Thread.activeCount()` — приблизительное число живых тредов;
- `ProcessHandle.current().info().totalCpuDuration()` — **кумулятивное CPU-время процесса**
  (JDK 9+, `java.lang.ProcessHandle`, именно `java.base`). Дельта за окно / (wall × cores) = CPU%.

Требует `java.management` (и потому опционально): счётчики и паузы GC, non-heap/metaspace,
пулы тредов, peak thread count.

Гипотеза (не проверена кодом, проверить в M2): на Kotlin/Native под Linux то же самое берётся из
`/proc/self/statm` (RSS) и `/proc/self/stat` (utime/stime), под macOS — `mach_task_basic_info`.
`kotlin.native.runtime.GC` даёт статистику своего GC, но API помечено экспериментальным.

## 2. Решения

### Р1. Агент агрегирует, сервер складывает *(отклонение от драфта)*

Драфт: агент кладёт событие на каждый запрос в `Channel`, сервер раз в минуту схлопывает сырьё в
минутные срезы.

Решение: **агент сам держит минутное окно** и раз в окно отправляет по одной серии на
(method, route, status_class): count, sum, max и разреженную гистограмму. Плюс **top-N самых
медленных запросов** окна отдельным списком — чтобы «что именно тормозило» не потерялось.

Почему:

- сервис на 1000 rps шлёт **один-два пакета в минуту** вместо 60 000 датаграмм; на UDP это разница
  между «работает» и «теряем половину»;
- потеря пакета = потеря одного окна одного сервиса, а не смещение выборки (при сырых событиях
  потери UDP систематически смещают перцентили — теряются, как правило, пики нагрузки, то есть
  ровно то, ради чего мониторинг ставят);
- у сервера пропадает фоновая таска схлопывания и таблица сырья: он просто пишет пришедшее окно;
- цена: перцентили приблизительные и агент чуть сложнее (см. Р2 и Риск 1).

### Р2. Гистограмма: экспоненциальные бакеты γ = 1.2, разреженная передача

`bucket = 0` для `duration < 1 ms`, иначе `bucket = ceil(ln(ms) / ln(1.2))`, всё, что > 10 с, — в
overflow-бакет. Это ~51 бакет на диапазон 1 мс … 10 с; относительная ширина бакета 20 %, значит
**погрешность перцентиля ≤ 20 %** (с линейной интерполяцией внутри бакета — на практике заметно меньше).

Передаются только непустые бакеты (`[[idx, count], …]`) — реальное распределение занимает 10–20
бакетов, так что серия укладывается в ~100 байт JSON.

Честная граница применимости, её надо держать в голове и писать в UI: этого достаточно для трендов,
алертов и «стало ли хуже после релиза», и **недостаточно** для формального SLA-репортинга
(«p99 = 412 мс» с двумя значащими цифрами metrik не даёт).

### Р3. Формат — JSON (kotlinx.serialization), не бинарь

При одном пакете в минуту на сервис экономия байт не окупает нечитаемый провод. `tcpdump` и
`nc -ul` должны показывать то, что можно прочитать глазами, — на этапе, когда протокол ещё не
устоялся, это важнее компактности. Бинарный кодек — отдельный пункт бэклога (M-42), включается
флагом, когда появится сервис, которому 1200 байт мало.

### Р4. Агент — KMP (`commonMain` + expect/actual)

`ktor-server-core` и `ktor-network` мультиплатформенны, поэтому вся логика плагина (хуки,
агрегатор, отправитель) живёт в `commonMain`. Платформенным остаётся только чтение системных
метрик: `expect fun readSystemSnapshot(): SystemSnapshot`.

Бонус, ради которого это и делается: metrik сможет мониторить нативные Ktor-сервисы — katcher
и **сам metrik-server** (dogfooding: сервер мониторинга, который не видно, — плохой сервер мониторинга).

### Р5. Дашборд — отдельный контейнер, сервер отдаёт только JSON

Из 1.3: тащить бандл Compose Wasm через нативный Ktor нечем. Поэтому `metrik-web` — статика в
nginx-контейнере, `metrik-server` — только `/api/**`, разводка по путям на уровне ingress/Traefik.
Никакого file-handler'а поверх okio в M1.

### Р6. Real-time в MVP не нужен

Окно агрегации минутное — SSE/WebSocket не даст ничего, чего не даст `polling` раз в 15–30 с.
`ktor-server-sse` под linux есть (1.1), так что дверь открыта, но в MVP — обычный опрос
(M-51 в бэклоге).

### Р7. Доверенная сеть + api-key, ingest наружу не выставляем

UDP не аутентифицируется и подделывается тривиально. Модель угроз честная: **ingest-порт живёт
только внутри кластера**, api-key в пакете отсекает чужие/случайные сервисы, а не злоумышленника.
UI-часть авторизуется как в katcher — заголовками от reverse proxy (`X-Auth-Request-User`,
`X-Auth-Request-Email`), своего логина metrik не имеет.

### Р8. Одна инсталляция = одна команда, мультитенантности нет

Модель: **инсталляция metrik принадлежит команде**, внутри неё — много сервисов, у каждого много
инстансов. Уровня «владелец/тенант» в схеме нет: ни `owner_id`, ни разделения данных внутри одной
базы. Команде нужна изоляция от другой команды — она поднимает свою инсталляцию (один бинарь и
один файл БД, это дёшево ровно настолько, чтобы такой ответ был честным).

Авторизация UI — как в katcher, без собственного логина: доверяем заголовкам reverse proxy
`X-Auth-Request-User` / `X-Auth-Request-Email`, без них `401`. Кто прошёл прокси — тот видит всё.
Следствие, которое надо написать в README крупно: **metrik без прокси перед UI ставить нельзя.**

### Р9. Хранение — SQLite через sqlx4k, схема сразу «оконная»

Сырья нет вообще (см. Р1), поэтому таблицы: минутные окна маршрутов, минутные системные снапшоты,
медленные сэмплы (retention 24 ч), часовые/дневные роллапы для долгой ретенции, состояния алертов.
Миграции — как в katcher, списком SQL + `PRAGMA user_version`
(`katcher/server/src/commonMain/kotlin/ru/workinprogress/katcher/db/Migrate.kt` — образец для копирования).

**Инстансы складываются на записи, минутки живут 48 часов.** Арифметика: 80 серий × 1440 окон ×
3 инстанса × 7 дней ≈ 2,4 млн строк и ~400 МБ на **один** сервис — несовместимо с обещанием
«лёгкий». Слияние инстансов в одну строку `(service_id, window_start, method, route, status)` плюс
48-часовая ретенция минуток дают порядка ×30. Цена: маршруты нельзя посмотреть в разрезе
конкретного пода; разрез по инстансам остаётся у системных метрик и у `absent`, где он
действительно нужен.

### Р10. Статус: класс для 1xx–3xx, точный код для 4xx/5xx

Успешный трафик однороден, и хранить `200`/`201`/`204` раздельно незачем. Ошибочный — наоборот:
`401` против `404` и `500` против `503` это «сломалась авторизация» против «клиент стучится не
туда» и «упало приложение» против «упала зависимость». Разница между этими парами и есть то, ради
чего смотрят на алерт, так что рост кардинальности на ошибочном трафике оправдан, а на успешном
его нет.

### Р11. Версия релиза ездит по проводу

Агент шлёт `rel` (тег образа / версия / git sha) раз в окно; смена значения пишется в `deploys` и
рисуется вертикальной отметкой на графиках. Двадцать байт в минуту за ответ на вопрос «после чего
стало хуже» — самая выгодная сделка во всём протоколе. В ключ серии версия **не** входит: это
удвоило бы кардинальность на каждом выкате.

Окружения (test/prod) отдельным полем **не** передаются: контуры разделены сетью, и на каждый
поднимается своя инсталляция. Один бинарь с одним файлом БД достаточно дёшев, чтобы это был
честный ответ, а не отговорка.

### Р12. Ingest-key один на инсталляцию, сервис заводится сам

Регистрации сервиса нет: ключ в конфиге сервера, первый пакет с новым `s` создаёт сервис.
Подключение — две строки в коде и переменная окружения, без похода в UI. Это осмысленно ровно
потому, что инсталляция принадлежит одной команде и живёт в доверенной сети (Р7, Р8): ключ отсекает
случайное, а не злонамеренное.

Обратная сторона названа прямо: опечатка в имени сервиса заводит фантом. Лечится кнопкой «удалить»;
ротация ключа — переменная окружения и рестарт.

## 3. Риски и открытые вопросы

**Риск 1. Приблизительные перцентили.** Смягчение: интерполяция внутри бакета, честная подпись в
UI, top-N медленных сэмплов рядом с графиком (они точные). Открыто: не занижать ли γ до 1.1 для
диапазона до 100 мс — решать после первых реальных данных.

**Риск 2. Потери UDP молча искажают картину.** Смягчение: в каждом пакете `seq`/`total` внутри окна
и монотонный счётчик окон инстанса — сервер видит и дырки в окне, и пропущенные окна, и показывает
их явно («данные неполные»), а не рисует ровный график по неполным данным. Проверить нагрузочно в M3.

**Риск 3. Кардинальность.** Даже шаблоны маршрутов могут разрастись (много инстансов × много
маршрутов × 5 классов статусов). Ограничение с обеих сторон: агент держит не больше `maxSeries`
(дефолт 200) уникальных серий за окно, лишнее сваливает в `<other>`; сервер режет ещё раз и логирует.

**Риск 4. Стоимость замера на горячем пути.** Цель — не более сотни наносекунд на запрос: снять
`TimeSource.Monotonic.markNow()`, на `ResponseSent` посчитать дельту и сделать инкремент в
`HashMap<SeriesKey, Bucket>` под сменяемым окном. Никаких аллокаций строк на запрос (ключ серии —
кэшированный объект на маршрут). Мерить бенчмарком в M2, а не верить на слово.

**Риск 5. Часы инстансов расходятся.** Окно нарезает агент по своим часам. Сервер использует
`window_start` из пакета, но отбрасывает окна, ушедшие в будущее/прошлое больше чем на 5 минут, и
показывает такие инстансы в UI как «часы разъехались».

### 1.5 `SelectorManager` съедает воркер `Dispatchers.Default` (Kotlin/Native)

Найдено при выкате в кластер и локализовано минимальной программой; воспроизводится однозначно.

**Каждый `SelectorManager` занимает воркер `Dispatchers.Default` своим `select()`-циклом
навсегда.** На Kotlin/Native размер этого пула привязан к числу ядер, поэтому на узле с двумя
ядрами двух селекторов достаточно, чтобы в пуле не осталось никого, кто возобновит корутину по
таймеру: **`delay` перестаёт срабатывать во всём процессе**.

Замер (бинарь linuxX64, под с двумя ядрами, `delay(1000)` в цикле):

| Селекторов | Тики `delay` |
|---|---|
| 1 | идут ровно по секунде |
| 2 | **не идут вовсе** |
| 3 | не идут вовсе |

У metrik-server селекторов было три: приёмник UDP, отправитель агента и движок Ktor CIO. Симптомы
выглядели как две несвязанные поломки — «не работает таймер» и «датаграммы не доходят», — но
причина одна: возобновлять континуации было некому.

Почему это не ловилось локально: на машине разработчика ядер пять, свободные воркеры остаются.
Ни эмуляция, ни ограничение `--cpuset-cpus` в Docker Desktop картину не воспроизводят — среда
сообщает рантайму другое число процессоров.

**Следствие для кода:** селекторный цикл обязан жить на собственном потоке
(`SelectorManager(newSingleThreadContext(...))`), а не на общем пуле. Для агента это критично
вдвойне: `SelectorManager()` в чужом процессе — это отобранный воркер у сервиса, в который агент
встроили, при обещании «отказ metrik не влияет на целевой сервис».

---

**Риск 6. Слияние инстансов на записи — read-modify-write.** Строка окна обновляется каждым
пришедшим инстансом, значит повторно доставленный пакет молча удвоит цифры. Защита — идемпотентность
по `(s, i, t, q)` и слияние в той же транзакции, что и приём. Проверяется тестом, а не рассуждением.
Смежное: роллап не трогает окна моложе 5 минут, иначе свернёт минуту, в которую ещё долетают пакеты
отстающих инстансов.

**Открытый вопрос 1.** Нужен ли HTTP-фолбэк транспорта (тот же JSON, но `POST /ingest`) для агентов
вне кластера. Гипотеза: нужен, но не в MVP.

**Открытый вопрос 2.** Лицензия. Проект открытый, как katcher, — но у самого katcher файла
`LICENSE` нет, то есть по умолчанию он «все права защищены» и юридически неиспользуем. Для metrik
это надо закрыть до первой публикации образа (Apache-2.0 или MIT — решение владельца).

### 1.6 Доменное имя на Kotlin/Native не разрешается — молчание агента

Найдено разбором «агент на native молчит»; воспроизводится тестом
`UdpSenderTest.a hostname endpoint should resolve and deliver`.

**`InetSocketAddress(host, port)` на Kotlin/Native имя не резолвит.** На JVM это делает сам
`InetSocketAddress`, поэтому одинаковый код работает на JVM и падает на нативе:

| Адрес в endpoint | JVM | Kotlin/Native |
|---|---|---|
| `127.0.0.1:9999` | работает | работает |
| `metrik-ingest:9999` | работает | `connect` падает с **EINVAL** |

Дальше складывается ловушка из трёх частей, и каждая по отдельности выглядит разумно:

1. агент **обязан** глотать ошибки отправки — иначе мониторинг ронял бы наблюдаемый сервис;
2. значит, сломанная отправка снаружи неотличима от исправной: метрик просто нет;
3. а «метрик нет» — это ровно то, что показывает правило `absent`. Мониторинг честно сообщал
   «сервис молчит» о совершенно живом сервисе, и виноват был он сам.

Почему не поймали раньше: единственный нативный агент, который работал, — самонаблюдение самого
metrik, а у него endpoint `127.0.0.1:$udpPort`, то есть резолвинг ему не нужен. Все остальные
нативные сервисы ходят по доменному имени сервиса Kubernetes и молчали с первого дня. Тесты были
зелёные, потому что `MetrikPluginTest` подставляет фейковый `MetrikSender`: настоящий сокет не
открывался ни разу.

**Решение** — резолвить имя самим через `getaddrinfo` (`HostResolver.native.kt`), предпочитая IPv4,
и делать это на каждое подключение: адрес пода меняется при переезде, и закешированный пережил бы
его молча. Числовой адрес проходит через ту же функцию без изменений.

**Вывод за пределами этого случая:** компонент, который по замыслу глотает свои ошибки, обязан
иметь тест против настоящего ввода-вывода. Фейк проверяет всё, кроме того единственного, что у
такого компонента может сломаться незаметно.

## 4. Что делать дальше
