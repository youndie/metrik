# metrik-web

## 1. Зона ответственности

SPA-дашборд: список сервисов, состояние алертов, графики по сервису, таблица маршрутов, список
медленных запросов. Пишет только пороги алертов и заглушение доставки — всё остальное чтение.

**Не отвечает за:** авторизацию (её делает reverse proxy перед `metrik-server`), хранение,
любую бизнес-логику агрегации — считает сервер.

## 2. Как раздаётся

**Статику отдаёт сам `metrik-server`** — один контейнер, один порт, один артефакт релиза (M-98).
Бандл лежит в образе по пути из `METRIK_WEB_ROOT`, каталог сканируется один раз на старте: файлы
вшиты в образ и меняться не могут.

Раньше рядом стоял отдельный контейнер с nginx, и research §Р5 объяснял, что иначе нельзя — на
Kotlin/Native нет `staticFiles`. Посылка верна, вывод оказался неверным: `staticFiles` там
действительно нет, но всё, что он делает (MIME, ETag, поиск предсжатого двойника, SPA-фолбэк),
пишется руками и умещается в два файла. Разбор — research §1.8, код —
`server/src/commonMain/.../web/WebAssets.kt` и `WebRoutes.kt`.

**Дашборд выключается**: `web.enabled: false` в чарте затирает `METRIK_WEB_ROOT`, и сервер
перестаёт отдавать статику; API, алертинг и MCP работают как работали. Причина не в размере образа,
а в памяти: страница разом открывает десятки соединений, и именно эта веерность растит пул потоков
сервера (M-99). Инсталляциям, которым хватает [клиента в терминале](metrik-cli.md) и MCP, платить
за это не нужно.

Образы собирает `.github/workflows/publish.yml`: нативный бинарь и wasm-бандл компилируются на
раннере, а Dockerfile только копирует готовое — Kotlin/Native внутри docker собирался бы десятки
минут на каждый образ.

**Грабля, которая ломается молча:** `index.html` не появляется сам. Compose-дистрибутив — это
`composeApp.js` и `.wasm`, грузить их некому. Оболочка лежит в
`composeApp/src/wasmJsMain/resources/index.html`.

У модуля есть второй таргет — **desktop-jvm** (`./gradlew :composeApp:run`). Он не деплоится и
существует только ради скорости цикла: wasm-сборка идёт минуты, а UI отлаживается одинаково.
Всё, что попадает в `commonMain`, обязано работать на обоих; платформенного кода в дашборде быть
не должно.

CORS на `metrik-server` нужен только для локальной разработки (`web` на `:8081`, сервер на `:8080`);
в проде оба за одним хостом.

## 3. Устройство модуля

Слои по фичам, как в остальных клиентах (скилл `client-feature-impl`):

```
web/
  core/{domain,data}      — UseCase-контракт, TimeSource, фабрика HttpClient
  navigation/             — Route : NavKey + синхронизация с историей браузера (expect/actual)
  ui/                     — тема, UI-кит, рельс, нижняя навигация, оболочка (AppShellViewModel)
  feature/<name>/
    domain/               — Repository (интерфейс) + по одному классу на операцию
    data/                 — RepositoryImpl поверх HttpClient
    ui/                   — ViewModel (UiState/UiAction/UiEvent) + пара Screen/Content
```

Три вещи здесь не декоративны:

* **Пути к API не собираются строками.** Классы `@Resource` объявлены один раз в `:shared`
  (`ru.workinprogress.metrik.api.Api`) и используются обеими сторонами: `ktor-server-resources` на
  сервере, `ktor-client-resources` в дашборде. Копия пути в клиенте протухает молча — переименовали
  роут, компилятор промолчал, сломалось у пользователя.
* **Навигация — стек, а не переменная.** Navigation 3 (`NavDisplay`, `Route : NavKey`), маршруты
  `@Serializable`. На wasm стек связан с историей браузера
  (`com.github.terrakok:navigation3-browser`): кнопки «назад/вперёд» и адресная строка — часть
  интерфейса, а не украшение.
* **Прокрутка одна на экран, отступы внутри неё.** `contentPadding` применяется **после**
  `verticalScroll`; повешенный снаружи паддинг сужает вьюпорт, и контент режется по внутренней
  границе.

## 4. Экраны

| Экран | Содержимое |
|---|---|
| Обзор | карточка на сервис: RPS, error rate, p95, состояние алерта, спарклайн за час |
| Сервис | графики RPS / latency (p50, p95, max) / errors за период + **вертикальные отметки деплоев**; переключатель 1ч / 24ч / 7д |
| Маршруты | таблица (метод, шаблон, статус, count, p50, p95, max), сортировка по любой колонке. Статус — точный код для 4xx/5xx, так что `401` и `404` видны отдельными строками |
| Медленные | последние медленные сэмплы за 24ч |
| Система | heap/RSS, CPU, треды, GC (если данные есть) — **единственный экран с разрезом по инстансам** |
| Алерты | активные, история срабатываний, пороги сервиса (единственная форма с записью) |

Обновление — `polling` раз в 15–30 с (research §Р6): окно агрегации минутное, SSE ничего не добавит.

## 5. Обязательные элементы честности в UI

Не косметика, а требование — иначе дашборд будет врать:

* перцентили подписаны как приблизительные (±20 %, ширина бакета);
* окна с флагом `partial` и пропущенные окна рисуются **разрывом линии**, а не нулём;
* инстанс с `clock_skew` помечен явно;
* отсутствие GC-данных — «нет данных», не «0»;
* при периоде глубже 48 часов видно, что данные часовые, а не минутные;
* у нативных сервисов подпись «RSS», а не «heap» — это разные величины
  ([feature-system-metrics](../features/feature-system-metrics.md)).

## 6. Чего в UI нет

Разреза маршрутов по инстансам — данные так не хранятся (см. [metrik-server](metrik-server.md)).
Списка инстансов как сущности: при rolling update они меняются каждый выкат, и список из сорока
мёртвых подов ничего не сообщает. Инстансы видны только на экране «Система» и в тексте алерта
`absent`.
