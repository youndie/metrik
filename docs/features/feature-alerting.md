# Алертинг в Telegram

## 1. Суть

Смотреть в дашборд никто не будет. Ценность мониторинга появляется в момент, когда он сам пишет
в Telegram «orders-api: 12 % пятисоток последние 3 минуты».

## 2. Правила v1

| Правило | Условие | Защита от ложных срабатываний |
|---|---|---|
| `error_rate` | доля 5xx за окно > порога (дефолт 5 %) | только если `count ≥ 20` за окно |
| `latency` | p95 > порога (дефолт 2000 мс) | K окон подряд (дефолт 3) |
| `memory` | heap used / heap max > порога (дефолт 90 %) | K окон подряд (дефолт 3) |
| `absent` | от сервиса нет ни одного окна дольше T (дефолт 3 мин) | считается **по сервису**, а не по инстансу |

`absent` — самое дешёвое и самое полезное правило: оно ловит «сервис умер», а этого не поймает ни
одно правило по нагрузке. Оно же ловит и обрыв сети до metrik — различить эти два случая метриками
нельзя, и текст нотификации должен это признавать («нет данных», а не «сервис упал»).

Почему по сервису: при rolling update поды пересоздаются, и правило «замолчал инстанс» срабатывало
бы на каждом выкате. Сервис жив, пока прислало окно хоть одно его окно-присылающее — этого и
достаточно. Инстансы, не присылавшие данных дольше суток, просто удаляются воркером ретенции и в
UI списком не показываются.

## 2а. Пороги: дефолты инсталляции + переопределение на сервис

Дефолты задаются переменными окружения сервера (`METRIK_ALERT_*`) и действуют на все сервисы.
Для конкретного сервиса пороги (и telegram-чат) переопределяются через
`PUT /api/admin/services/{id}/alerts` — строка в `alert_rules` с непустым `service_id` перекрывает
дефолтную.

Это единственная мутирующая операция в UI, и она добавлена сознательно: без неё один шумный сервис
заставляет ослабить пороги для всех, после чего алерты перестают что-либо значить.

## 3. Машина состояний

```
OK ──(условие выполнено)──▶ FIRING ──(условие не выполняется K окон)──▶ OK
                              │
                              └─ нотификация при входе + напоминание не чаще cooldown (30 мин)
```

* Нотификация шлётся при **переходе** состояния, не при каждой проверке.
* Возврат в OK тоже нотифицируется («восстановилось, длилось 14 мин»).
* Гистерезис (K окон на выход) — иначе один шумный порог даст флаппинг и алерты перестанут читать.
* Cooldown ограничивает напоминания по длящемуся инциденту.

## 4. Доставка

Telegram Bot API `sendMessage` через ktor-client (CIO работает на Kotlin/Native). Токен и чат по
умолчанию — env-переменные; шумный сервис можно увести в свой чат через переопределение правил.
Без токена правила всё равно считаются и видны в UI, просто без нотификаций.

Ошибка доставки не роняет воркер и не теряет состояние: следующая проверка попробует снова.

## 6. Сценарии (BDD)

### Сценарий: всплеск ошибок на пустом сервисе не будит ночью
* **Дано:** порог `error_rate` = 5 %, минимум 20 запросов
* **Когда:** за минуту было 3 запроса, из них 1 с 500 (33 %)
* **Тогда:** алерт не срабатывает

### Сценарий: флаппинг гасится
* **Дано:** p95 колеблется вокруг порога
* **Когда:** условие перестало выполняться на одном окне из трёх
* **Тогда:** алерт остаётся FIRING, повторных нотификаций нет

### Сценарий: сервис пропал
* **Дано:** сервис слал окна и перестал
* **Когда:** прошло 3 минуты без единого окна
* **Тогда:** срабатывает `absent`, в тексте — «нет данных от сервиса», без утверждения о причине

### Сценарий: rolling update не будит дежурного
* **Дано:** сервис из трёх подов, идёт последовательная замена подов
* **Когда:** старый под замолчал, новый ещё не прислал первое окно
* **Тогда:** `absent` не срабатывает, пока хоть один инстанс сервиса присылает окна

### Сценарий: шумный сервис не ослабляет пороги остальным
* **Дано:** дефолтный порог `error_rate` = 5 %, для сервиса `legacy-import` выставлено 30 %
* **Когда:** у `legacy-import` 20 % ошибок, у остальных 6 %
* **Тогда:** `legacy-import` в OK, остальные в FIRING

### Сценарий: Telegram недоступен
* **Дано:** токен валиден, но API отвечает 5xx
* **Когда:** нужно отправить нотификацию
* **Тогда:** воркер не падает, алерт остаётся FIRING, попытка повторяется на следующей проверке
