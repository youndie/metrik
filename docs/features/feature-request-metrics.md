# Метрики HTTP-запросов

## 1. Суть

Владелец сервиса видит по каждому Ktor-сервису: сколько запросов в секунду, какая доля ошибок,
как долго отвечают маршруты (p50/p95/max) и какие конкретно запросы были самыми медленными —
не подключая ничего, кроме одного плагина.

## 2. Бизнес-правила

* Единица агрегации — `(метод, шаблон маршрута, статус)` за окно в 1 минуту.
* Статус — класс для 1xx–3xx и точный код для 4xx/5xx: `401` должен отличаться от `404`,
  а `500` от `503`.
* Метка маршрута — **шаблон** (`/users/{id}`), не сырой путь: иначе кардинальность неограниченна.
* Окна разных инстансов за одну минуту сливаются в одну строку на записи; разреза по инстансам
  у маршрутов нет — он есть только у системных метрик.
* Смена версии релиза отмечается на графиках: «стало хуже» без «после чего» бесполезно.
* Запрос, не сматчившийся ни на один маршрут, попадает в серию `<unmatched>`.
* Свыше `maxSeries` (200) уникальных серий за окно всё лишнее сваливается в `<other>` —
  агент никогда не растёт по памяти неограниченно.
* Перцентили приблизительные, погрешность ≤ 20 % (ширина бакета); UI обязан это подписывать.
* Потери и неполные окна показываются разрывом линии, а не нулём.
* Медленные сэмплы не содержат тела, заголовков, query string и сырого пути.

## 3. Как это работает

```
Ktor-сервис                             metrik-server                 metrik-web
  hook Metrics      → t0
  hook ResponseSent → Δt, status, route
        ↓ inc в окне (in-memory)
  [окно закрыто, раз в 60 с]
        ↓ UDP ≤1200 B, N пакетов        → валидация k/s/v/t
                                        → INSERT route_windows
                                        → roll-up раз в час
                                                    ↓ GET /api/services/{id}/timeseries → графики
```

Аутентификация ingest — api-key в пакете, доверенная сеть (research §Р7). Аутентификация чтения —
заголовки reverse proxy.

## 5. Сценарии (BDD)

### Сценарий: маршрут с параметром схлопывается в один ряд
* **Дано:** сервис с маршрутом `get("/users/{id}")`, агент установлен
* **Когда:** пришло 100 запросов на разные `id`
* **Тогда:** в окне ровно одна серия `GET /users/{id} 2xx` с `count = 100`, а не 100 серий

### Сценарий: 404 не создаёт серию на каждый несуществующий путь
* **Дано:** тот же сервис
* **Когда:** пришло 50 запросов на 50 разных несуществующих путей
* **Тогда:** одна серия `<unmatched>` с `count = 50`

### Сценарий: перцентиль считается по сумме инстансов
* **Дано:** три инстанса одного сервиса шлют окна за одну и ту же минуту
* **Когда:** дашборд запрашивает p95 за эту минуту
* **Тогда:** в базе одна строка с суммой счётчиков и сложенными побакетно гистограммами, p95
  берётся из неё (а не как среднее трёх p95)

### Сценарий: повторно пришедший пакет не удваивает окно
* **Дано:** окно инстанса уже слито в строку `route_windows`
* **Когда:** тот же пакет `(s, i, t, q)` приходит второй раз
* **Тогда:** `count` строки не меняется

### Сценарий: 401 и 404 — разные ряды
* **Дано:** на один и тот же маршрут приходят и неавторизованные запросы, и запросы к
  несуществующему объекту
* **Когда:** дашборд показывает таблицу маршрутов
* **Тогда:** это две отдельные строки, `401` и `404`, а не одна `4xx`

### Сценарий: деплой виден на графике
* **Дано:** инстансы начали присылать `rel = "1.4.212"` вместо `1.4.211`
* **Когда:** дашборд рисует период, в который это случилось
* **Тогда:** на графике вертикальная отметка деплоя в момент первого окна с новой версией

### Сценарий: потерянный пакет виден
* **Дано:** окно нарезано на 2 пакета, второй не дошёл
* **Когда:** дашборд рисует эту минуту
* **Тогда:** точка помечена `partial`, линия рисуется с разрывом, а не значением «меньше, чем было»

### Сценарий: metrik-server недоступен
* **Дано:** агент установлен, `endpoint` указывает в никуда
* **Когда:** сервис обрабатывает запросы
* **Тогда:** запросы обрабатываются штатно, латентность не растёт, в логах сервиса нет
  исключений от metrik, потери видны в счётчике агента
